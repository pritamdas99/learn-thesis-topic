# A2C and A3C: advantage actor-critic

Companion code: [08_a2c_a3c.py](08_a2c_a3c.py). Requires PyTorch.

[tensors and autograd](../01_foundations/02_tensors_autograd.md). You should know
softmax, log-probabilities, entropy, Bellman targets, and why we `detach` targets

## 1. What problem are we solving now?

Use the same corridor again:

```text
       0          1          2          3          4
    [END] <--> [room] <--> [START] <--> [room] <--> [GOAL]
     reward 0                                     reward +1
```

Left is action `0`, right is action `1`; entering 4 gives reward 1 and ends the
episode, entering 0 gives 0 and ends it. The discount in the script is
$\gamma=0.95$.

REINFORCE ([lesson 05](05_reinforce_actor_critic.md)) waits for a whole episode
and uses the complete Monte Carlo return, just like [lesson 07](07_monte_carlo.md).
That is unbiased but noisy, and nothing can be learned until the episode ends.

**Advantage actor-critic** keeps two things in one model:

- an **actor**, a policy $\pi_\theta(a\mid s)$ that chooses actions;
- a **critic**, a value estimate $V_\phi(s)$ of expected future return.

After a short **segment** of at most $n$ steps, the critic fills in the rest of
the return, so the agent can update without waiting for the episode to finish.

A2C and A3C are two ways to run several copies of the environment
("workers") at once. **A2C** waits for all workers and makes one synchronized
update. **A3C** lets each worker update the shared parameters whenever it is
ready. The loss is the same; only the coordination differs.

## 2. Notation

| Symbol | Meaning | Code |
| --- | --- | --- |
| $s_t,a_t,r_t$ | State, sampled action, reward at step $t$ of a segment | `state`, `action`, `rewards[t]` |
| $\pi_\theta(a\mid s)$ | Actor: softmax of the first two outputs | `out[:2].softmax(-1)` |
| $V_\phi(s)$ | Critic: the third output | `out[2]` |
| $n$ | Maximum segment length | `steps=5` |
| $\gamma$ | Discount factor | `gamma=0.95` |
| $R_t$ | Bootstrapped n-step return target | `targets[t]` |
| $\hat A_t$ | Advantage estimate $R_t-V_\phi(s_t)$ | `advantage[t]` |
| $H(\pi(\cdot\mid s))$ | Entropy of the action distribution | `entropies[t]` |
| $c_v,c_H$ | Critic and entropy coefficients | `0.5`, `0.01` |
| $\operatorname{sg}(\cdot)$ | Stop-gradient: treat as a constant | `.detach()` / `torch.no_grad()` |

The model is a single `nn.Linear(5, 3)` applied to a one-hot state
`torch.eye(5)[state]`: two actor logits and one value per state. Because the
input is one-hot and there is no hidden layer, each state effectively has its
own three numbers, and the actor rows and the value row are separate weights
inside one layer. Larger implementations often share a hidden network between
actor and critic; this script does not have shared hidden features.

## 3. The n-step return: real rewards, then the critic

For a segment starting at $t$ that runs $n$ steps without a terminal,

$$\boxed{R_t^{(n)}=\sum_{k=0}^{n-1}\gamma^k r_{t+k}+\gamma^n V_\phi(s_{t+n})}.$$

Three cases decide what goes at the end:

| What ended the segment | Bootstrap value used | Why |
| --- | --- | --- |
| True terminal (entered 0 or 4) | $0$ | There is no future after termination |
| Segment hit `steps=5` in a nonterminal state | $V_\phi(s_{t+n})$ | The episode continues; the critic estimates the rest |
| (Not in this script) time-limit truncation | $V_\phi$ of the real next state | A cutoff is not a terminal |

If a true terminal occurs before $n$ steps, the segment is simply shorter. The
script implements this with `break` when `terminal` is true, and then starts the
next segment from state 2 (a reset). After a nonterminal segment the worker
continues from the state where it stopped.

**Small arithmetic check.** Rewards $[0,1]$, $\gamma=0.9$, endpoint value 0.5:

$$R_0^{(2)}=0+0.9(1)+0.9^2(0.5)=0.9+0.405=1.305.$$

If that endpoint were a true terminal, the bootstrap is 0 and $R_0=0.9$. With
current value $V(s_0)=0.4$, the advantages are $1.305-0.4=0.905$ and
$0.9-0.4=0.5$.

### Every step in a segment gets its own target

The code computes targets with a backward recursion, starting from the bootstrap:

```python
total = torch.tensor(0.) if terminal else model(torch.eye(5)[state])[2]
for reward in reversed(rewards):
    total = reward + gamma*total
    targets.insert(0, total)
```

So the first step uses an $n$-step return, the second an $(n-1)$-step return,
and the last step a 1-step return. Example with `steps=5`, $\gamma=0.95$, all
five rewards zero, and a nonterminal end with $V(s_5)=0.8$:

| $t$ | Steps of real reward | $R_t=0.95^{5-t}(0.8)$ |
| --- | --- | --- |
| 4 | 1 | 0.76 |
| 3 | 2 | 0.722 |
| 2 | 3 | 0.6859 |
| 1 | 4 | 0.651605 |
| 0 | 5 | 0.61902475 |

The segment length is a dial: `steps=1` is a pure one-step TD target
(maximal reliance on the critic, low variance, more bias); a very long segment
approaches the Monte Carlo return of REINFORCE (no critic in the target, higher
variance).

## 4. The loss: actor, critic, entropy

$$\hat A_t=R_t-V_\phi(s_t)$$

$$L_{\mathrm{actor}}=-\frac1B\sum_t\log\pi_\theta(a_t\mid s_t)\,
\operatorname{sg}(\hat A_t),\qquad
L_{\mathrm{critic}}=\frac1B\sum_t\big(V_\phi(s_t)-\operatorname{sg}(R_t)\big)^2,$$

$$\boxed{L=L_{\mathrm{actor}}+c_vL_{\mathrm{critic}}-c_H\,\overline{H}(\pi_\theta)}$$

with $B$ the number of steps in the segment, $c_v=0.5$, $c_H=0.01$, and
$\overline H$ the mean entropy over the segment.

| Term | What it does |
| --- | --- |
| $L_{\mathrm{actor}}$ | Raises $\log\pi$ of actions with positive advantage, lowers it for negative |
| $L_{\mathrm{critic}}$ | Regresses $V_\phi(s_t)$ toward the target $R_t$ |
| $-c_H\overline H$ | Rewards uncertainty in the policy, encouraging exploration |

**Why the stop-gradients?** The targets are computed under `torch.no_grad()`,
so the critic loss only moves $V_\phi(s_t)$, not the bootstrap value. In the
actor term, `advantage.detach()` makes the advantage a fixed weight. Without it,
minimising the actor loss would also push gradients into the critic, letting
the "actor objective" improve by distorting value predictions rather than by
changing the policy.

In the script the critic term is written `0.5*advantage.square().mean()`; since
`targets` has no gradient, that equals $0.5\,L_{\mathrm{critic}}$.

## 5. A fully worked first segment from the script

The trainers call `torch.manual_seed(7)` before `make_model()`. The initial
model gives, for state 2, logits $(0.0165, 0.3132)$ and value $-0.5725$; for
state 3, logits $(0.0145, 0.0766)$ and value $-0.6445$. The initial right
probabilities are $0.5736$ in state 2 and $0.5155$ in state 3.

A2C worker 0 uses `torch.Generator().manual_seed(20)`. Its first segment
samples right, right: `2 --R--> 3 --R--> 4`, which ends at a true terminal.

**Targets** (bootstrap 0 because of termination):

$$R_1=1+0.95(0)=1,\qquad R_0=0+0.95(1)=0.95.$$

**Advantages:**

| $t$ | $s_t$ | $V(s_t)$ | $R_t$ | $\hat A_t=R_t-V(s_t)$ | $\pi(\text{right}\mid s_t)$ | $\log\pi$ | Entropy |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 0 | 2 | −0.5725 | 0.95 | 1.5225 | 0.5736 | −0.5558 | 0.6823 |
| 1 | 3 | −0.6445 | 1 | 1.6445 | 0.5155 | −0.6625 | 0.6927 |

The entropy of $(0.4264, 0.5736)$ is $-(0.4264\ln0.4264+0.5736\ln0.5736)\approx0.6823$,
slightly below the two-action maximum $\ln2\approx0.6931$.

**Loss pieces** ($B=2$):

$$L_{\mathrm{actor}}=-\tfrac12[(-0.5558)(1.5225)+(-0.6625)(1.6445)]
=\tfrac12(0.8462+1.0895)\approx0.9679,$$

$$0.5\,L_{\mathrm{critic}}=0.5\cdot\tfrac12(1.5225^2+1.6445^2)
=0.5\cdot\tfrac12(2.3180+2.7044)\approx1.2557,$$

$$c_H\overline H=0.01\cdot\tfrac12(0.6823+0.6927)\approx0.0069.$$

$$L\approx0.9679+1.2557-0.0069=2.2167.$$

Calling `rollout_loss` on this model with generator seed 20 returns 2.21669 and
next state 2 (reset after terminal). Both advantages are positive because the
critic started pessimistic (negative values), so this segment's contribution
to the gradient pushes the probability of right up in states 2 and 3 and pushes
both values up. (In A2C it is averaged with three other workers' segments before
the optimizer step.)

## 6. A2C: synchronous updates

`train_a2c(updates=250, workers=4)`:

1. Seed the model with `torch.manual_seed(7)`; create Adam with `lr=0.025`.
2. Give each of the 4 workers its own generator (seeds 20, 21, 22, 23) and its
   own environment state, all starting at 2.
3. For each of the 250 updates, every worker runs `rollout_loss` with the
   **same current parameters**, the 4 losses are averaged, and one optimizer
   step is taken.

```text
params v0 ─┬─ worker 0 segment ─┐
           ├─ worker 1 segment ─┤
           ├─ worker 2 segment ─┼─ mean loss → one step → params v1 ─┬─ ...
           └─ worker 3 segment ─┘
```

Because all gradients come from one parameter version, nothing is stale.
Collection here is a plain sequential loop for simplicity; vectorised
environments can run the same logic in parallel. Note one detail: the script
averages the four per-segment *means*, so a 2-step segment and a 5-step segment
get equal weight in the update.

## 7. A3C: asynchronous updates

`train_a3c(updates_per_worker=250, workers=4)` runs 4 worker functions on a
`ThreadPoolExecutor`. Each worker repeats 250 times:

1. **Copy** the global parameters into its local model (under the lock).
2. **Collect** a segment and **backpropagate** locally (no lock held).
3. **Apply** its local gradient to the global model with one SGD step
   (`lr=0.03`, under the lock).

While worker 0 is in step 2, other workers can finish step 3, so by the time
worker 0 applies its gradient, the global parameters may already be newer than
the ones it used. Its gradient is **stale**. This is the central distinction
from A2C. See the [original A3C paper](https://arxiv.org/abs/1602.01783).

```text
worker 0:  copy v3 ── collect + backward ──────────── apply → v6
worker 1:     copy v4 ── collect + backward ── apply → v5
worker 2:  ... (each step applies whenever ready; no barrier)
```

What the teaching implementation does and does not do:

| Feature | In this script? |
| --- | --- |
| Concurrent CPU threads, local model copies, independent generators (seeds 40–43) | Yes |
| Lock around parameter reads and writes | Yes, prevents conflicting writes |
| Barrier that waits for all workers | No |
| Lock-free Hogwild updates, shared RMSProp from the paper | No (plain SGD) |
| Deterministic results | No: thread scheduling changes the update order |
| Meant as a speed benchmark | No; at scale, processes are often preferable to Python threads |

Both trainers process the same number of segments (4 × 250 = 1000), but A2C makes
250 Adam steps on averaged gradients while A3C makes 1000 SGD steps on single
segments. The optimizers and learning rates differ, so the two printed results
are not a controlled comparison of the algorithms.

## 8. Map the explanation to the script

| Code | Meaning |
| --- | --- |
| `nn.Linear(5, 3)` | Two actor logits and one value per one-hot state |
| `probs = out[:2].softmax(-1)` | $\pi_\theta(\cdot\mid s)$ |
| `torch.multinomial(probs, 1, generator=generator)` | Sample $a_t$ with a per-worker generator |
| `logs.append(probs[action].log())` | $\log\pi_\theta(a_t\mid s_t)$ |
| `-(probs*probs.log()).sum()` | Entropy $H$ |
| `values.append(out[2])` | $V_\phi(s_t)$, with gradient |
| `rewards.append(float(state == 4))` | Reward 1 only on entering the goal |
| `if terminal: break` | Shorter segment at a true terminal |
| `torch.tensor(0.) if terminal else model(...)[2]` | Bootstrap: 0 at terminal, $V_\phi(s_{t+n})$ otherwise |
| `total = reward + gamma*total` (reversed) | n-step targets $R_t$ |
| `advantage = targets-torch.stack(values)` | $\hat A_t$ |
| `-(torch.stack(logs)*advantage.detach()).mean()` | Actor loss |
| `0.5*advantage.square().mean()` | Critic loss, $c_v=0.5$ |
| `-0.01*torch.stack(entropies).mean()` | Entropy bonus, $c_H=0.01$ |
| `return loss, 2 if terminal else state` | Reset to 2 after a terminal, else continue |
| `torch.stack(losses).mean().backward()` + `optimizer.step()` | A2C: one synchronized update |
| `local.load_state_dict(global_model.state_dict())` | A3C: refresh local copy |
| `shared.grad = private.grad.detach().clone()` + `optimizer.step()` | A3C: apply a possibly stale gradient |

A3C right probabilities: [0.9246646165847778, 0.9479199647903442, 0.9141947627067566]

Each list is $\pi(\text{right}\mid s)$ for states 1, 2, 3 after training,
up from the initial $0.5819, 0.5736, 0.5155$. A2C is reproducible across runs
(sequential, seeded). A3C's digits change from run to run because thread timing
changes the order of updates, exactly as Section 7 predicts. Exact digits may
also differ across PyTorch versions.

The only assertion is `torch.isfinite(p).all()`: it checks that training did
not produce NaN or infinity. It does **not** check that the policy learned to
move right; read the printed numbers for that.

## 10. Practice calculations

1. Rewards $[0,0,1]$ end in a true terminal, $\gamma=0.95$. What are the targets?
   **$[0.9025, 0.95, 1]$.**
2. Rewards $[0,0]$, nonterminal end, $V(s_2)=0.6$, $\gamma=0.95$. Targets?
   **$R_1=0.57$, $R_0=0.5415$.**
3. With $V(s_0)=0.7$ in question 2, what is $\hat A_0$, and does the actor push
   the sampled action's probability up or down? **$0.5415-0.7=-0.1585$; down.**
4. What is the entropy of $\pi=(0.5,0.5)$, and what does the entropy term add
   to the loss? **$\ln2\approx0.6931$; $-0.01(0.6931)\approx-0.0069$.**
5. If you remove `.detach()` from the actor's advantage, which parameters get
   extra gradient? **The value output (critic row), through $-V_\phi(s_t)$ inside
   the advantage.**
6. Why can A3C produce different numbers on two runs with the same seeds?
   **Threads interleave differently, so gradients are applied to different
   parameter versions in a different order.**

Exercises: set `steps` to 1, then 10, and explain the change in bootstrap
reliance and return variance. Remove the entropy bonus and compare five seeds.
Do not infer algorithm superiority from one short corridor run.
